# Dashboard Experience V3

План и состояние реализации после PR №3. Части V3 ниже реализованы в TASK 04 и пересмотрены по TASK 04.1; результаты проверок и ограничения приведены в VERIFICATION.md.

## Отправная точка и направление

`Calculator.tsx` управляет формой и результатами; `evaluate` проверяет ввод, а математическое ядро возвращает `totalBytes`, `bytesPerDay`, `cameraCount`, `retention` и `summaries`. Уже работают темы light/dark/system, распределение групп, клавиатурные переходы и reduced motion. Сохранить эти возможности и текущие ограничения расчёта.

Направление: premium light/dark dashboard, indigo/violet/blue accents, bento grid, выразительные карточки результатов, аккуратные SVG-графики и современные контролы. Светлая тема — ясные поверхности и мягкие тени; тёмная — глубокий графит, различимые уровни и сдержанное свечение. Цвет дополняет подписи, а композиция помогает сравнивать параметры и результат. Сверка с конкретными графическими референсами не выполнялась: в доступных материалах V3 их нет. Оформление оценено по заданному направлению и сравнению с production V2.

## Пересмотр композиции — TASK 04.1, PR №4

Пять верхних карточек заменены парой разного масштаба: акцентный hero и полный баланс HDD. Ниже — три явно подписанных примера, редактор, прогноз, схема камер и распределение. Прототип на реальных компонентах просмотрен в четырёх сочетаниях desktop/mobile и light/dark до добавления новых функций; сравнение с TASK 04 показало изменение иерархии и расположения, а не только палитры.

- `StorageCapacity.tsx`: SVG-кольцо, требуемый/доступный объём, остаток либо дефицит. Приёмка: все единицы, дробная ёмкость, равенство, нули, предел, отсутствие прежних значений при ошибке; независимые bigint-эталоны в тестах.
- `CameraSystem.tsx`: одна SVG-пиктограмма на группу, реальные параметры из формы, выбор переводит фокус в редактор. Приёмка: 10 000 камер не размножают пиктограммы; 100 групп доступны в прокручиваемом списке, выделение и удаление согласованы с распределением.
- `scenarios.ts`, `ScenarioPresets.tsx`: Дом/Магазин/Офис заменяют реальную форму. Число камер, средний битрейт, кодек, разрешение, расписание, срок и HDD явно подписаны. Ручное изменение снимает соответствие пресету, «Сбросить» возвращает исходные настройки. Примеры не являются рекомендацией битрейта.
- `GroupCard.tsx`: основные поля отделены от сворачиваемых метаданных; native details доступны клавиатуре и изначально открыты. `ArchiveForecast.tsx`: линейный area chart дополнен контрольными точками и визуальным инспектором; точное форматированное значение также доступно под графиком и через range.

Новые пакеты, коэффициенты и внешние ресурсы не используются. Математическое ядро не меняется; новые SVG используют те же результаты. Точность целого количества байтов сохраняется в поддерживаемом диапазоне; дробный ввод ёмкости и доли/проценты остаются приближёнными Number-представлениями. Итоги проверок — в VERIFICATION.md.

## Семантика графиков

- Источник — только успешный результат существующего ядра; при ошибках графики скрываются вместе с результатом. Формулы и валидация в `src/domain/storage/calculator.ts` и `config.ts` не меняются.
- Накопление начинается с условно пустого архива: `bytesPerDay × прошедшие сутки`, горизонт — выбранный срок хранения. Это усреднённая модель повторяющегося расписания, а не фактическая почасовая телеметрия. Для ежедневных/ночных интервалов явно подписать усреднение.
- Ёмкость HDD — уже введённая доступная ёмкость в выбранных единицах. Срок заполнения берётся из `retention`; если он вне горизонта, показать пояснение вместо расширения оси за допустимые пределы. Не изображать циклическую перезапись: такой модели нет.
- При нулевом потоке — нулевая линия и «Без ограничения»; при нулевой ёмкости и положительном потоке — заполнение в момент 0. Не делить на ноль. Точки ограничить небольшим фиксированным числом; якорь дня 0 формировать в представлении, не передавая недопустимый срок ядру.
- Итоговая точка совпадает с `totalBytes`, доли групп — с `summary.bytes / totalBytes`. Округлять только подписи; не округлять исходные байты. Не добавлять фиктивные тренды, загрузку CPU, онлайн-статусы камер, прогноз реального VBR или исходную занятость HDD.

## Общая проверка перед слиянием каждого PR реализации

- `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`, `npx playwright install chromium`, `npm run test:e2e`, `git diff --check`, `git status`. На Windows использовать текущий `PLAYWRIGHT_BROWSERS_PATH` внутри проекта; не переустанавливать зависимости при работающем preview.
- Playwright: 320, 360, 375, 390, 430, 768, 1024, 1440, 1920 px; обе темы, 200% текста, клавиатура, reduced motion, длинные ошибки и большие числа. Проверить отсутствие переполнения и ошибок консоли, доступность графиков через текст и отсутствие управления только по hover/цвету. Axe дополняет ручную проверку применимых требований WCAG 2.2 AA.
- Сохранить и реально просмотреть снимки до/после desktop/mobile. Сравнить bundle и одинаковые сценарии ввода при 1/100 группах; локальные замеры отделять от удалённого CI. В каждом PR указать новые проверки, ограничения и результат CI.
- Использовать текущие React/TypeScript, lucide-react, Vitest/RTL, Playwright/axe. Новые компоненты выделять по конкретной ответственности; не строить универсальную dashboard/chart-систему. Сторонние шрифты, chart-пакеты и фиктивная навигация не нужны. Публикация и merge — отдельное решение владельца.
